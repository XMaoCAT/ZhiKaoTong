# 小体量上传/排队/热更新系统推荐方案细则
> 适用目标：当前在 Windows 下通过 `start.bat` 一键启动，并自动打开浏览器进行内网测试；后期可平滑迁移到 Ubuntu / Linux。
>
> 推荐原则：
> 1. 当前阶段尽量零依赖、易启动、易调试。
> 2. 架构必须支持排队、进度、压力自适应。
> 3. 后期迁移 Linux 时，只改部署方式，不改核心架构。
> 4. 热更新优先做前端资源、配置、插件，不强行热替换后端核心进程。

---

## 1. 最终推荐技术栈

### 1.1 前端

必须使用：

```text
HTML + JavaScript
```

可选框架：

```text
原生 JS / Vue / React / Svelte
```

推荐当前阶段：

```text
原生 HTML + JS
```

原因：

1. 最简单。
2. 方便热更新。
3. 无需复杂构建。
4. 后期也可以替换成 Vue/React 构建产物。

前端必须实现：

```text
上传进度显示
排队位置显示
处理进度显示
请勿退出提示
版本更新提示
SSE 自动重连
```

---

### 1.2 后端

推荐使用：

```text
Node.js 20 LTS 或更高
Fastify
```

推荐理由：

1. Windows / Linux 都支持。
2. 开发速度快。
3. 适合 I/O 密集型上传任务。
4. 前后端语言统一。
5. 后期迁移 Linux 无需更换技术栈。

推荐后端模块：

```text
fastify
@fastify/static
better-sqlite3
```

如果不想使用原生 SQLite 模块，也可以临时替换为：

```text
lowdb / JSON 文件存储
```

但正式建议仍使用：

```text
SQLite
```

---

### 1.3 数据库

当前推荐：

```text
SQLite
```

原因：

1. 不需要单独安装数据库服务。
2. Windows 下启动简单。
3. Linux 下也完全兼容。
4. 小体量系统足够使用。

数据库文件建议放在：

```text
./data/app.db
```

后期如果并发明显增大，可迁移到：

```text
PostgreSQL
```

但当前不建议一开始就部署 PostgreSQL。

---

### 1.4 任务队列

当前阶段不建议在 Windows 上强依赖 Redis。

推荐：

```text
SQLite 任务表 + Node.js 内置任务调度器
```

也就是：

```text
任务写入 SQLite
Node.js 定时扫描可执行任务
根据服务器压力动态并发执行
```

后期如果迁移到 Linux，并且压力明显增大，可以升级为：

```text
Redis + BullMQ
```

但架构上必须提前抽象：

```text
QueueAdapter
```

默认实现：

```text
SQLiteQueueAdapter
```

可选实现：

```text
RedisQueueAdapter
```

---

### 1.5 实时推送

推荐：

```text
SSE，Server-Sent Events
```

不优先使用 WebSocket 的原因：

1. 当前只需要服务端向客户端推送进度。
2. SSE 更简单。
3. HTTP 兼容性好。
4. 小服务器开销更低。

推送接口：

```text
GET /api/tasks/:taskId/events
```

---

### 1.6 文件上传

必须使用：

```text
分片上传
```

推荐分片大小：

```text
2MB - 8MB
```

小服务器推荐：

```text
5MB
```

必须支持：

```text
上传进度
断点续传
上传失败重试
上传完成确认
```

## 4. 启动方式细则

### 4.1 Windows 启动

必须支持：

```text
双击 start.bat 启动
```

`start.bat` 至少要做以下事情：

```text
1. 进入当前目录
2. 检查 Node.js 是否安装
3. 如果不存在 node_modules，则自动安装依赖
4. 启动 server.js
5. 延迟几秒后自动打开浏览器
6. 控制台保持运行，方便看日志
```

推荐 `start.bat` 示例：

```bat
@echo off
chcp 65001 >nul
cd /d %~dp0

title Local Upload Server

where node >nul 2>nul
if errorlevel 1 (
    echo [错误] 未检测到 Node.js，请先安装 Node.js LTS。
    pause
    exit /b 1
)

if not exist node_modules (
    echo [提示] 首次运行，正在安装依赖...
    call npm install
)

echo [提示] 正在启动服务...
start "UploadServer" cmd /k node server.js

timeout /t 3 >nul
start "" "http://127.0.0.1:8080"

echo [提示] 服务已启动。
echo [提示] 本机访问:
echo         http://127.0.0.1:8080
echo [提示] 内网访问请使用服务器局域网 IP，例如:
echo         http://192.168.x.x:8080
pause
```

---

### 4.2 服务监听地址

服务必须监听：

```text
0.0.0.0
```

不能只监听：

```text
127.0.0.1
```

否则内网其他设备无法访问。

推荐配置：

```text
HOST=0.0.0.0
PORT=8080
```

---

### 4.3 启动后控制台必须显示访问地址

Node 服务启动后，应输出：

```text
服务已启动
本机访问: http://127.0.0.1:8080
内网访问: http://192.168.x.x:8080
```

这样即使浏览器没有自动打开，也可以手动访问。

## 6. 前端页面功能细则

前端必须包含以下状态：

```text

CHECKING_UPDATE
WAITING_UPLOAD_SLOT
UPLOADING
UPLOAD_COMPLETED
QUEUED
PROCESSING
SUCCESS

```

---

### 6.1 版本更新提示

前端启动时必须请求：

```text
GET /api/version
```

返回格式：

```json
{
  "version": "2026.07.08-01",
  "notes": "优化上传进度显示",
  "forceUpdate": false
}
```

前端必须将返回版本与本地版本对比。

如果版本不同，显示：

```text
发现新版本
是否立即更新？
```

用户点击更新后：

```text
1. 清除本地缓存
2. 重新加载页面
3. 使用最新静态资源
```

---

### 6.2 上传中提示

上传开始后，前端必须显示：

```text
数据正在上传，请勿退出
```

并显示：

```text
当前进度：35%
已上传：12.5 MB / 36.0 MB
速度：1.2 MB/s
```

同时必须监听页面关闭：

```js
window.addEventListener("beforeunload", (event) => {
  event.preventDefault();
  event.returnValue = "数据正在上传，请勿退出";
});
```

---

### 6.3 排队提示

当服务端返回排队状态时，前端必须显示：

```text
当前请求前还有 12 个任务未处理
请耐心等待，不要退出
```

如果服务端能返回预计等待时间，也可以显示：

```text
预计等待：45 秒
```

---

### 6.4 处理进度提示

任务开始处理后，前端必须显示：

```text
正在处理，请稍候
当前进度：48%
当前步骤：正在导入数据
```

进度更新必须优先通过 SSE 接收。

如果 SSE 断开，必须自动降级为轮询：

```text
每 3 秒请求一次任务状态
```

## 7. 上传流程细则

### 7.1 申请上传

前端提交前必须先请求：

```text
POST /api/uploads/apply
```

请求体：

```json
{
  "fileName": "data.zip",
  "fileSize": 104857600,
  "fileType": "zip",
  "bizType": "import"
}
```

服务端根据当前压力返回两种结果。

---

### 7.2 允许上传

返回：

```json
{
  "status": "allowed",
  "uploadId": "up_20260708_0001",
  "chunkSize": 5242880,
  "chunkCount": 20
}
```

前端开始分片上传。

---

### 7.3 进入排队

返回：

```json
{
  "status": "queued",
  "ticketId": "tk_20260708_0001",
  "queuePosition": 12
}
```

前端显示：

```text
当前请求前还有 12 个任务未处理
```

---

## 8. 分片上传接口细则

### 8.1 初始化上传

```text
POST /api/uploads/init
```

请求：

```json
{
  "fileName": "data.zip",
  "fileSize": 104857600,
  "chunkSize": 5242880
}
```

返回：

```json
{
  "uploadId": "up_20260708_0001",
  "chunkSize": 5242880,
  "chunkCount": 20
}
```

---

### 8.2 上传单个分片

```text
PUT /api/uploads/:uploadId/chunks/:chunkIndex
```

例如：

```text
PUT /api/uploads/up_20260708_0001/chunks/0
```

请求体：

```text
二进制分片内容
```

返回：

```json
{
  "uploadId": "up_20260708_0001",
  "chunkIndex": 0,
  "received": true
}
```

---

### 8.3 查询上传进度

```text
GET /api/uploads/:uploadId
```

返回：

```json
{
  "uploadId": "up_20260708_0001",
  "status": "uploading",
  "chunkCount": 20,
  "uploadedChunkCount": 9,
  "progress": 45
}
```

---

### 8.4 完成上传

```text
POST /api/uploads/:uploadId/complete
```

服务端必须检查：

```text
1. 分片数量是否完整
2. 文件大小是否一致
3. 文件是否损坏
4. 是否重复提交
```

返回：

```json
{
  "taskId": "task_20260708_0001",
  "status": "queued",
  "queuePosition": 6
}
```

## 9. 任务处理流程细则

任务状态必须包含：

```text
QUEUED
PROCESSING
SUCCESS
FAILED
CANCELLED
```

任务表必须记录：

```text
id
user_id
upload_id
type
status
priority
seq
progress
message
result_url
error_message
created_at
updated_at
started_at
finished_at
```

---

### 9.1 排队位置计算

推荐使用自增序号：

```text
seq
```

提交任务时：

```text
生成新的 seq
写入任务表
状态为 QUEUED
```

当前任务排队位置：

```text
queuePosition =
当前状态为 QUEUED 且 seq 小于当前任务 seq 的任务数量 + 1
```

这样前端可以显示：

```text
当前请求前还有 xx 个任务未处理
```

---

### 9.2 任务进度推送

推荐使用 SSE：

```text
GET /api/tasks/:taskId/events
```

事件类型：

```text
queue
progress
done
error
```

示例：

```text
event: queue
data: {"queuePosition":6}

event: progress
data: {"progress":35,"message":"开始处理"}

event: progress
data: {"progress":78,"message":"正在写入结果"}

event: done
data: {"status":"SUCCESS","resultUrl":"/api/results/xxx"}
```

## 10. 压力自适应细则

服务端必须根据压力自动调节：

```text
允许上传槽位
任务处理并发数
是否进入排队模式
是否拒绝新任务
```

---

### 10.1 监控指标

至少监控：

```text
CPU 使用率
内存使用率
当前活跃上传数
当前排队任务数
当前处理中任务数
事件循环延迟
磁盘剩余空间
```

---

### 10.2 压力等级

建议分为三级：

```text
LOW
NORMAL
HIGH
```

---

### 10.3 LOW 压力

条件示例：

```text
CPU < 50%
内存 < 70%
排队任务 < 50
磁盘剩余充足
```

行为：

```text
逐步增加上传槽位
逐步增加任务并发
允许新任务直接进入上传
```

---

### 10.4 NORMAL 压力

条件示例：

```text
CPU 50% - 85%
内存 70% - 85%
排队任务 50 - 200
```

行为：

```text
保持当前并发
新任务视情况排队
```

---

### 10.5 HIGH 压力

条件示例：

```text
CPU > 85%
内存 > 85%
排队任务 > 200
磁盘剩余不足
```

行为：

```text
降低任务并发
减少上传槽位
新任务进入排队
必要时拒绝低优先级任务
返回预计等待时间
```

---

### 10.6 自适应检查周期

推荐：

```text
每 5 秒检查一次
```

调节必须平滑，不能瞬间大幅波动。

推荐策略：

```text
压力过高：并发降低 20% - 30%
压力过低：并发增加 1 个
最小上传槽位：1 - 2
最大上传槽位：10 - 20
最小任务并发：1
最大任务并发：2 - 4
```

小服务器不要设置过高并发。

## 11. 热更新细则

热更新必须拆成两类：

```text
1. 前端热更新
2. 后端可热更部分
```

---

### 11.1 前端热更新

前端资源必须版本化。

推荐文件：

```text
/public/version.json
```

内容：

```json
{
  "version": "2026.07.08-01",
  "notes": "优化上传进度显示",
  "forceUpdate": false
}
```

静态资源推荐：

```text
/public/app.js?v=2026070801
/public/style.css?v=2026070801
```

或者：

```text
/public/app.2026070801.js
/public/style.2026070801.css
```

`index.html` 必须设置为不缓存或短缓存。

推荐响应头：

```text
Cache-Control: no-cache
```

---

### 11.2 前端更新提示流程

```text
1. 前端启动时请求 /api/version
2. 对比本地保存的 version
3. 如果不同，弹出更新提示
4. 用户点击更新
5. 清除缓存或重新加载资源
6. 页面 reload
```

---

### 11.3 后端热更新边界

后端不建议直接热替换核心代码。

推荐允许热更新的内容：

```text
配置
文案
前端页面
插件
任务规则
字段映射
校验规则
处理脚本
```

不建议热更新的内容：

```text
HTTP 服务核心
数据库连接
队列核心
进程生命周期
鉴权核心
文件存储核心
```

---

### 11.4 配置热更新

配置文件：

```text
/config/config.json
```

服务端可以监听文件变化：

```text
修改配置后无需重启
```

可热更新配置：

```text
最大上传槽位
最大任务并发
排队阈值
是否开启降级
前端版本号
公告内容
```

---

### 11.5 插件热更新

任务处理逻辑建议拆成插件。

例如：

```text
/src/plugins/example-task.js
```

插件结构：

```js
export default {
  name: "example-task",
  version: "2026.07.08-01",
  async run(context) {
    context.updateProgress(10, "开始处理");
    // 处理逻辑
    context.updateProgress(100, "处理完成");
    return {
      success: true
    };
  }
};
```

服务端通过配置指定当前使用哪个插件版本。

新增插件时：

```text
1. 新增新版本插件文件
2. 修改配置中的当前版本
3. 新任务使用新版本
4. 旧任务继续使用旧版本
5. 无需重启核心服务
```

## 12. Windows 到 Linux 迁移细则

当前方案必须保证：

```text
Windows 可运行
Linux 可运行
```

因此必须遵守：

```text
1. 不使用 Windows 专有路径
2. 不写死盘符
3. 所有路径使用 Node.js path.join
4. 配置文件使用相对路径
5. 数据库文件可迁移
6. 存储目录可迁移
```

---

### 12.1 Linux 启动方式

迁移到 Ubuntu 后，可直接运行：

```bash
npm install
node server.js
```

正式环境推荐：

```bash
pm2 start server.js --name upload-server
pm2 save
```

或者使用：

```bash
systemd
```

---

### 12.2 Linux 推荐部署方式

推荐顺序：

```text
1. Node.js 直接运行
2. PM2 守护运行
3. systemd 服务
4. Docker Compose
```

当前阶段不建议一开始上 Kubernetes。

---

### 12.3 迁移时需要复制的内容

至少包含：

```text
项目代码
config/
public/
src/
data/
storage/
package.json
package-lock.json
```

迁移后需要检查：

```text
端口是否放行
文件目录权限是否正确
Node.js 版本是否一致
数据库文件是否可读写
上传目录是否可写
```

## 13. 数据库设计细则

### 13.1 上传记录表

```sql
CREATE TABLE uploads (
  id TEXT PRIMARY KEY,
  user_id TEXT,
  file_name TEXT,
  file_size INTEGER,
  chunk_size INTEGER,
  chunk_count INTEGER,
  uploaded_chunk_count INTEGER DEFAULT 0,
  status TEXT DEFAULT 'INIT',
  storage_path TEXT,
  created_at TEXT,
  updated_at TEXT
);
```

状态：

```text
INIT
UPLOADING
COMPLETED
FAILED
```

---

### 13.2 任务表

```sql
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,
  user_id TEXT,
  upload_id TEXT,
  type TEXT,
  status TEXT DEFAULT 'QUEUED',
  priority INTEGER DEFAULT 0,
  seq INTEGER,
  progress INTEGER DEFAULT 0,
  message TEXT,
  result_url TEXT,
  error_message TEXT,
```

## 16. 验收标准

系统上线前必须满足以下验收标准。

---

### 16.1 Windows 验收

```text
1. 双击 start.bat 可启动
2. 首次运行可自动安装依赖
3. 启动后自动打开浏览器
4. 本机可访问 http://127.0.0.1:8080
5. 内网其他设备可通过局域网 IP 访问
6. 控制台显示访问地址
```

---

### 16.2 上传验收

```text
1. 可选择文件
2. 可显示上传进度
3. 上传中关闭页面有提醒
4. 上传失败可重试
5. 上传完成可进入任务队列
6. 大文件不会一次性卡死服务
```

---

### 16.3 排队验收

```text
1. 服务器忙时任务进入排队
2. 前端能显示当前请求前还有多少个任务
3. 排队位置能动态减少
4. 任务开始处理后能收到通知
5. 多个用户同时提交不会串任务
```

---

### 16.4 压力自适应验收

```text
1. 高负载时新任务进入排队
2. 高负载时不会继续无限增加处理并发
3. 低负载时能逐步恢复处理速度
4. 磁盘不足时能拒绝新上传
5. 队列过长时能提示等待
```

---

### 16.5 热更新验收

```text
1. 修改前端文件并更新版本号后，用户能收到更新提示
2. 用户点击更新后能加载新版本页面
3. 修改配置后无需重启服务即可生效
4. 新增插件后新任务可使用新插件
5. 核心服务不因普通业务修改而重启
```

---

## 17. 最终推荐方案总结

当前最适合你的方案是：

```text
Node.js 20 LTS
+ Fastify
+ SQLite
+ 本地分片上传
+ 内置任务队列
+ SSE 进度推送
+ 压力自适应调度器
+ HTML 前端版本化热更新
+ Windows start.bat 启动
+ 后期迁移 Linux / PM2 / systemd
```

当前阶段不建议引入：

```text
Kubernetes
Docker Swarm
复杂微服务
Redis 强依赖
PostgreSQL 强依赖
消息中间件
```

后期如果压力明显增大，再按以下顺序升级：

```text
1. SQLite -> PostgreSQL
2. 内置队列 -> Redis + BullMQ
3. 单机 Worker -> 独立 Worker 进程
4. 本地存储 -> MinIO / OSS / S3
5. 单机部署 -> 多台服务器 + Nginx 负载均衡
```

这样既能保证现在 Windows 下一键启动、内网测试简单，也能保证后期迁移到 Ubuntu / Linux 时不需要推翻重做。
